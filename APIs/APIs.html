Part 1 - API Fundamentals and Background

Ground Rules for Research Integrity & Compliance

  • Prefer official APIs and bulk downloads over scraping
  • Respect terms of use, rate limits, and institutional policy
  • Avoid collecting PII/PHI
  • Use caching and delays to minimize server load
  • Document provenance: what you requested, when, from where

What is an API?

An Application Programming Interface (API) is a structured way to request data from a service.

For researchers, APIs are “programmable search + download”:

  • Predictable formats (often JSON, sometimes XML or CSV)
  • Documented inputs (parameters)
  • Standardized outputs (fields)

Why APIs are preferred

  • Reproducible: same query, same retrieval method
  • More stable: APIs change less often than website layouts
  • Automatable: supports batching, scheduling, and pipelines
  • Transparent: explicit parameters, documentation, and usage rules

Common Research workflow

API Request ──► JSON / XML Response ──► Parse & Flatten in R ──► Data Frame (Table) ──► (Optional) Save as CSV

Common Data Formats: CSV, JSON, and XML

The Data Journey

  1. What the API sends back: JSON or XML
    • Hierarchical, nested key-value structures optimized for web transit.
  2. What R turns it into: Data Frame / Tibble
    • R parses and “flattens” the nested JSON into rows and columns in memory so you can immediately run dplyr or ggplot2.
  3. What you can export to: CSV
    • A flat, plain-text file format you can save to disk, open in Excel, or share with collaborators.

Note

💡 Bottom Line: Web systems speak JSON/XML. Researchers analyze Tables. R acts as the translator between the two.

CSV (Comma-Separated Values)

Raw CSV Text:

id,age,sex
101,42,F
102,35,M

JSON (JavaScript Object Notation)

Raw JSON Structure:

[
  {
    "id": 101,
    "age": 42,
    "sex": "F"
  },
  {
    "id": 102,
    "age": 35,
    "sex": "M"
  }
]

Note

JSON stores data as nested key–value structures: flexible and web-friendly commonly used in modern APIs may require “flattening” into tables

XML (eXtensible Markup Language)

Raw XML Structure:

<participants>
  <participant>
    <id>101</id>
    <age>42</age>
    <sex>F</sex>
  </participant>
  <participant>
    <id>102</id>
    <age>35</age>
    <sex>M</sex>
  </participant>
</participants>

Note

  • XML organizes data using nested tags
  • older but still widely used in biomedical and government systems
  • highly structured and descriptive
  • commonly seen in legacy APIs and document-based databases

Core vocabulary

  • Endpoint: the URL for a resource (e.g., /search)
  • Method: GET (retrieve), POST (submit query)
  • Parameters: filters like ?year=2023&state=CT
  • Auth: key/token, sometimes OAuth
  • Rate limits: requests per time period
  • Pagination: page/offset/cursor for large results
  • Response: JSON objects you parse into tables

Note

What is pagination?

Pagination is how an API delivers large result sets in smaller “pages” to control load and response size.

Why pagination exists:

  • prevents oversized responses
  • improves reliability
  • supports rate limiting

Common HTTP methods (what they mean)

  • GET — retrieve data (most common for research data pulls)
  • POST — submit a query or create a record (common for complex searches; also for systems like REDCap when writing data)
  • PUT/PATCH — update a record (more common in operational systems than public datasets)
  • DELETE — remove a record (rare in public data APIs)

Note

Research norm: you’ll primarily use GET, and occasionally POST for “search” endpoints or authenticated systems.

Status codes you will see (and how to respond)

  • 200 OK — success
  • 400 Bad Request — your parameters are malformed
  • 401 Unauthorized — missing/invalid token
  • 403 Forbidden — you’re authenticated but not allowed (permissions/terms)
  • 404 Not Found — wrong endpoint or resource ID
  • 429 Too Many Requests — you hit a rate limit (slow down; retry later)
  • 500/503 — server problems (retry with backoff)

How researchers use APIs (examples)

  • Literature: retrieve PubMed metadata for reproducible searches
  • Safety: monitor OpenFDA adverse event reports
  • Trials: query ClinicalTrials.gov trial registries
  • EHR & Clinical: extract patient cohort records via REDCap or SMART on FHIR
  • Oncology & Genomics: query patient outcomes and tumor data via NCI GDC
  • Surveillance: download public health indicators and dashboards
  • Context: integrate Census covariates into analyses
  • Biomedical data: fetch gene expression datasets and biosample metadata from NCBI GEO

API workflow (the “researcher loop”)

  1. Identify source + documentation
  2. Draft a query (fields, filters, time range)
  3. Request data (respect limits)
  4. Validate + clean
  5. Save raw + processed data
  6. Record provenance (URL, params, date, version)

PubMed (NCBI E-utilities) — Literature Metadata

Key Research Use Cases

  • Reproducible Literature Workflows: Script PubMed queries to rerun searches automatically and log exact record counts.
  • Synthesizing Evidence: Pull titles, abstracts, and publication dates directly into R/Python for screening.
  • MeSH & Bibliometric Analysis: Harvest Medical Subject Headings and citation metadata for field mapping.

⚠️ NCBI Usage Guidelines

  • Rate Limits: 3 requests/sec default \(\rightarrow\) 10 requests/sec with a free NCBI API Key.
  • Identification: Always pass your email and tool name in API calls so NCBI doesn’t block your IP.
  • Output Format: E-utilities returns XML (use R’s rentrez or xml2 packages to parse into tables).

ClinicalTrials.gov — Trial Registry Metadata

Key Research Use Cases

  • Landscape Scans: Find trials by condition, drug/intervention, location, phase, or sponsor type.
  • Meta-Research & Compliance: Compare primary outcomes to published literature and monitor reporting compliance (FDAAA 801).
  • Eligibility Criteria Mining: Extract inclusion/exclusion criteria text for computable phenotype design.

Note

💡 API Practicalities: Uses the modernized v2 REST API (JSON output). No API key is required, making it ideal for quick scripting and reproducible workflows.

openFDA — Adverse Events & Drug Labeling

💊 Research Use Cases

  • Pharmacovigilance & Safety Signals: Scan post-marketing FDA adverse event reports (FAERS) for unexpected side effects.
  • Drug Labeling & Package Inserts: Search structured drug labels for contraindications, black box warnings, or active ingredients.
  • Medical Devices & Recalls: Query device clearance data (510k), enforcement reports, and recall actions.

🔑 API Quick Facts

  • Auth: 🟢 No key required for testing (Optional free key raises limit to 240 req/min)
  • Format: JSON | Endpoint: https://api.fda.gov/drug/event.json
  • Teaching Highlights:
    • Native count parameter for instant aggregations without downloading raw records
    • Perfect for teaching API search parameters, filtering, and pagination (limit & skip)
  • openFDA is built on Elasticsearch, meaning its search parameter syntax allows complex Boolean logic directly in the URL query string.
  • Highlight the count parameter: instead of downloading 50,000 JSON records to tabulate in R, count=patient.drug.medicinalproduct.exact lets the API do the aggregation server-side and return summary counts instantly!

CDC Open Data — Socrata & SoQL Queries

Key Research Use Cases

  • Surveillance & Dashboards: Query municipal and national health indicators (e.g., NCHS mortality data, surveillance trends).
  • Server-Side Data Subsetting: Filter massive datasets on CDC servers before pulling them into R/Python.

💡 SoQL (Socrata Query Language) Syntax

Socrata APIs support SQL-style parameters in the request URL: * $select=date, state, cases — Select only columns of interest * $where=state='CT' AND cases > 100 — Apply logical filters * $limit=5000 — Control payload size

Example Endpoint: https://data.cdc.gov/resource/{dataset_id}.json?$where=state='CT'

Census API — Population Context & Social Determinants

🏙️ Research Use Cases

  • Population Denominators: Convert raw disease/outcome counts into standardized rates (e.g., per 100,000 population).
  • Social Determinants of Health (SDoH): Integrate neighborhood-level covariates (median household income, poverty rate, education, internet access, health insurance coverage).
  • Fine-Grained Geographies: Query small administrative units—from state and county down to ZIP Code Tabulation Areas (ZCTAs), Census Tracts, and Block Groups.
  • Trend & Disparities Analysis: Compare multi-year American Community Survey (ACS 1-year and 5-year) estimates over time.

📊 Key Datasets & Products

  • ACS (American Community Survey): Annual sample survey; 5-year estimates offer high precision at small geographies (Tract/ZCTA). Includes estimates (E) and Margins of Error (M).
  • Decennial Census: Complete 10-year enumeration (2000, 2010, 2020) for exact total counts and basic demographics.
  • Emphasize that in public health/biomedical informatics, outcome data rarely comes with demographic denominators—the Census API provides those denominators.
  • Mention ACS Margins of Error (MOEs): unlike simple administrative databases, ACS data always includes sampling uncertainty.

UMLS API — Medical Terminologies & Crosswalking

🩺 Research Use Cases

  • Terminology Crosswalking: Map concepts across different coding systems (e.g., bridge an ICD-10 billing code to a SNOMED CT clinical term or RxNorm drug concept).
  • Concept Normalization: Standardize free-text clinical notes or diagnostic terms to unique UMLS Concept Unique Identifiers (CUIs).
  • Semantic Relationships: Query parent/child hierarchies, synonyms, and definitions across 200+ biomedical vocabularies (LOINC, MeSH, CPT, etc.).
  • Phenotype & Cohort Building: Expand clinical query definitions by fetching all related source-asserted codes for a disease or treatment.

📊 Key Metathesaurus Features

  • CUIs (Concept Unique Identifiers): Universal cluster IDs that link identical meanings across distinct source vocabularies.
  • Semantic Network: Categorizes concepts into broad semantic types (e.g., Disease or Syndrome, Pharmacologic Substance).
  • UMLS is maintained by the NIH National Library of Medicine (NLM).
  • Emphasize that in biomedical informatics, different databases use different coding standards (e.g., EHRs use SNOMED/LOINC, pharmacy data uses RxNorm, billing uses ICD-10). UMLS is the “rosetta stone” connecting them.
